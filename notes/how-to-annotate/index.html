    怎么写批注¶

    两条路，先选一条¶

    这本书有两套批注渠道，用途不同，不要混用。

    页面底部的「批注与讨论」 正文里的 📝 我的批注 框
    存在哪 GitHub Discussions Markdown 文件，进 git
    手机上能写吗 能，提交即显示 能，但要走 GitHub 编辑器
    写完要发布吗 不用 要跑 gh-deploy
    适合写什么 随手记、提问、勘误 正式补进正文的笔记

    日常随手记、想到就问 → 用页底那栏，最省事，手机点开就能写，提交完立刻显示。

    想让笔记变成正文的一部分（比如一段解释、一个更正）→ 用 📝 框，代价是得回电脑跑一次发布。

    三种标记¶

    这本书用三个视觉标记来区分三类内容。都是普通 Markdown，没有插件依赖，git diff 能看，能回滚。

    1. 📝 我的批注 —— 绿色¶

    用于你自己的笔记、疑问、心得。

    !!! quote "📝 我的批注 · 2026-11-06 · v0.1"
    这里写你的笔记。可以多行。
    缩进四个空格即可。

    效果：

    📝 我的批注 · 2026-11-06 · v0.1

    这里写你的笔记。可以多行。

    2. 🆕 版本补充 —— 金色¶

    用于"后来补进文档的内容"。标题里必须带版本号。

    !!! success "🆕 版本补充 · v0.2 · 2026-11-06"
    这一段是后来补的。版本号让你能看出这本书的生长轨迹。

    效果：

    🆕 版本补充 · v0.2 · 2026-11-06

    这一段是后来补的。

    3. ⚙️ 推断存疑 —— 橙色¶

    用于"这是我的推断，不是源码实证"。看到这个框，你可以怀疑它。

    !!! warning "⚙️ 这是推断，不是源码原文"
    这句话是我根据代码形态推测的，源码里没有明写。

    完整流程：提问 → 回答 → 补进文档¶

    这是这本书设计的核心循环。

    ① 你读到某一段，有疑问
        ↓
② 你来问我（任意方式描述）
        ↓
��� 我解释
        ↓
④ 我问你：「要不要把这段补进书里？」
        ↓
⑤ 你说要 → 我写进对应章节，打上 🆕 版本补充 框
        ↓  同时更新「批注汇总」页的版本表
⑥ 你说不用 → 我只在对话里解释，文档不动

    这个循环的意义：你的每一个困惑都会变成文档的一个增量。这本书是跟你一起长出来的，不是一次性写完就冻住的。

    版本号规则¶

    变化 版本号
    新增一整章 次版本号 +1（v0.1 → v0.2）
    补充某一段的解释 次版本号 +1
    修正错别字 / 链接 修订号 +1（v0.1 → v0.1.1）
    全书结构重排 主版本号 +1（v0 → v1）

    当前版本：v0.1（2026-11-06 首次成稿）

    版本表记在哪¶

    记在两处：

    1. 每个 🆕 框的标题里 —— 让人知道这一段是什么时候补的
    2. 批注汇总 顶部的版本表 —— 让人知道整本书的演化

    怎么写你自己的笔记¶

    页面底部那栏（手机首选）¶

    每页正文下面有一个「批注与讨论」区，背后是 GitHub Discussions。

    1. 在输入框里写，支持 Markdown
    2. 点「Comment」（第一次要先授权 Giscus 应用）
    3. 提交即显示，刷新一下就能看到

    不需要跑任何命令，不需要重新发布。批注存在仓库的 Discussions 里，点这个链接能看到全部： github.com/Jacky-Firswy/mini-agent-harness/discussions

    ⚙️ 两种批注互不相通

    页底的讨论不会自动出现在正文里，正文的 📝 框也不会出现在讨论里。它们是两套存储。

    想让某条讨论变成正文的一部分，得我手动搬过去，打上 🆕 版本补充 框。

    直接改文件¶

    文档是纯 Markdown，你可以直接用任何编辑器打开 docs/ 下的文件。

    推荐做法：在每章末尾留的那个批注位里写。

    用网站右上角的「编辑此页」按钮（手机上推荐）¶

    每个页面右上角有一个铅笔图标。点它，会直接在浏览器里打开这一页对应的 Markdown 文件（GitHub 的网页编辑器）。

    1. 点铅笔 → 页面跳到 GitHub 的编辑界面
    2. 找到这页末尾的 !!! quote "📝 我的批注" 那个框
    3. 在缩进四空格的正文里写你的话
    4. 拉到底部，点 Commit changes

    手机上也能用，只要浏览器里登录着 GitHub 账号。

    ⚙️ 静态站不能「直接保存」批注

    GitHub Pages 只发静态文件，没有任何能写入内容的后端。网站本身存不了你的批注，所有修改都必须落成一次 git 提交。

    所以"编辑此页"本质上是帮你跳到 GitHub 的编辑器，而不是让你在网页里直接批注。

    提交之后还要发布一次¶

    用上述方式提交后，改动进了仓库，但线上页面还不会变，要跑一条命令：

    python -m mkdocs gh-deploy --strict

    这条命令目前只能在装了 mkdocs 的那台电脑上跑。

    一条建议¶

    不要只写"不懂"。 写具体一点：

    • ❌ "事件流看不懂"
    • ✅ "为什么 5 秒超时是合理的？如果模型思考很久但一直不输出，会不会被误判成结束了？"

    越具体的问题，答案越能变成文档的一个好章节。

    重建网站¶

    改完 Markdown 后，本地预览会自动刷新（mkdocs serve 有热重载）。

    如果是要生成静态文件：

    python -m mkdocs build

    产物在 site/ 目录。site/ 已在 .gitignore 里，因为它是生成物。

    发布到公网（手机也能看）¶

    站点已经托管在 GitHub Pages：

    https://jacky-firswy.github.io/mini-agent-harness/

    改完文档后，一条命令就能更新线上版本：

    git add docs mkdocs.yml
git commit -m "文档：补充 xxx"
git push origin main
python -m mkdocs gh-deploy --strict

    最后那条 gh-deploy 会构建、推到 gh-pages 分支，然后 GitHub Pages 自动生效（大约 1~3 分钟）。

    为什么不用 GitHub Actions 自动发布¶

    本来配了一个工作流，push 就自动构建。但它启动即失败，报错是：

    The job was not started because your account is locked due to a billing issue.

    这是账号计费问题，不是仓库配置问题。 所以现在的流程是手动跑 gh-deploy。等计费问题解决后，可以再把工作流加回来。

    本地局域网访问（手机同一 WiFi）¶

    如果只是临时给同一 WiFi 下的手机看，可以不推公网：

    python -m mkdocs serve -a 0.0.0.0:8000

    然后手机访问 http://<本机局域网IP>:8000/（本机 IP 用 ipconfig 查）。

    -a 0.0.0.0 是必须的 —— 默认的 127.0.0.1 是回环地址，只有本机能连，手机永远打不开。另外 Windows 防火墙要放行这个端口，否则也会被拦住。
